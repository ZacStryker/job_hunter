## Intent

**Problem:** The recent-activity feed in `GET /api/stats` derives "applied" events from the date-only `dateApplied`, which `toIso()` pins to midnight (`T00:00:00Z`). So a same-day application always sorts below that day's status/resume/cover-letter events, which carry full ISO timestamps.

**Approach:** Add a new user-owned `appliedAt` column holding a full ISO timestamp, written server-side in lockstep with `dateApplied` in the PATCH handler. The feed prefers `appliedAt ?? dateApplied` for the applied event's timestamp, letting same-day applications interleave by time-of-day. No backfill; legacy rows keep their midnight fallback.

## Boundaries & Constraints

**Always:**
- `appliedAt` is user-owned: never in any `onConflictDoUpdate.set` block, never client-settable (not in `jobPatchSchema` / PATCH allowlist).
- Server sets `appliedAt = new Date().toISOString()` on first apply (when `applied` flips true and no existing value), and clears it to `null` on un-apply — exactly mirroring the existing `dateApplied` write in the same handler.
- Migration generated by `bun run db:generate` — never hand-written. Commit the generated SQL.
- Add `appliedAt: z.string().nullable()` to `jobSchema` in `src/shared/schemas.ts`.
- DB column name `applied_at` (snake_case); Drizzle `casing: 'camelCase'` maps it.

**Ask First:**
- Any change to the apply/un-apply semantics of `dateApplied` itself, or to feed sort order beyond the applied-event timestamp source.

**Never:**
- No backfill of existing rows.
- No UI change.
- No new PATCH-accepted field; `appliedAt` is not in the request schema.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First apply | `PATCH {applied:true}`, row has no `dateApplied` | `dateApplied` = today (date-only), `appliedAt` = full ISO now | N/A |
| Un-apply | `PATCH {applied:false}` | both `dateApplied` and `appliedAt` cleared to `null` | N/A |
| Re-apply already applied | `PATCH {applied:true}`, `dateApplied` already set | `dateApplied` unchanged (existing behavior); `appliedAt` only set when previously null | N/A |
| Feed timestamp, new row | row has `appliedAt` | applied event uses `appliedAt` (real time-of-day) | N/A |
| Feed timestamp, legacy row | `appliedAt` null, `dateApplied` set | applied event falls back to `toIso(dateApplied)` (midnight) | N/A |

**Acceptance Criteria:**
- Given an un-applied job, when `PATCH {applied:true}`, then `appliedAt` is a full ISO datetime (contains `T` and is not `...T00:00:00Z`) and `dateApplied` is today's date-only string.
- Given an applied job with `appliedAt` set, when `PATCH {applied:false}`, then both `appliedAt` and `dateApplied` are `null`.
- Given a morning `status_change` event and a same-day afternoon `appliedAt` on another job, when `GET /api/stats`, then the `applied` event appears before the `status_change` event in `recentActivity` (descending sort).
- Given a legacy row with `appliedAt` null but `dateApplied` set, when `GET /api/stats`, then the applied event timestamp is the midnight `toIso(dateApplied)` value (unchanged behavior).

## Design Notes

The PATCH apply branch becomes (mirroring existing `dateApplied` logic exactly):

```ts
if (patch.applied !== undefined) {
  updateFields.applied = patch.applied
  if (patch.applied && !existing.dateApplied) {
    updateFields.dateApplied = new Date().toISOString().split('T')[0]
    updateFields.appliedAt = new Date().toISOString()
  } else if (!patch.applied) {
    updateFields.dateApplied = null
    updateFields.appliedAt = null
  }
}
```

Guard on `!existing.dateApplied` (not `!existing.appliedAt`) so first-apply detection stays identical to current behavior — re-applying an already-applied legacy row won't fabricate an `appliedAt`.
